# 과제 1 · 희소 벡터와 밀집 임베딩 검색의 통제 비교

> **핵심 질문:** 같은 문서와 같은 정답 집합에서 TF–IDF와 문장 임베딩은 어떤 질의에
> 성공하거나 실패하며, 그 차이를 토큰·벡터·평가지표로 설명할 수 있는가?

|항목|내용|
|---|---|
|수행 형태|개인|
|교과목 반영|10%|
|권장 작업량|10–14시간|
|연결 수업|2주차 토큰화, 5주차 문장 임베딩, 7주차 검색 평가|
|필수 환경|Python 3.10+, Pandas, scikit-learn, Sentence Transformers 또는 동등 모델|
|제출|실행 가능한 Colab/Notebook, 데이터·평가 CSV, 기술 보고서, AI 사용 기록|

마감 시각과 제출 위치는 LMS 공지를 따른다. 공통 실행·협업·AI 정책은
[과제 운영 안내](README.md)를 먼저 읽는다.

## 1. 학습목표

과제를 완료하면 다음을 할 수 있어야 한다.

1. 검색 문제의 사용자, 검색 단위, 관련성 기준과 오류 비용을 운영적으로 정의한다.
2. 한국어 문서를 일관된 스키마로 정제하고 데이터 출처·라이선스·한계를 기록한다.
3. TF–IDF 희소 검색기와 밀집 임베딩 검색기를 동일한 인터페이스로 구현한다.
4. Precision@k, Recall@k, MRR, nDCG@k를 직접 계산하고 작은 예제로 검증한다.
5. 개발용 질의와 최종 평가 질의를 분리해 모델 선택 편향을 방지한다.
6. 평균 점수뿐 아니라 질의별 순위와 실패 유형으로 두 표현의 차이를 설명한다.
7. 실행환경, 모델 revision, seed와 결과 파일을 남겨 제3자가 실험을 재현하게 한다.

## 2. 문제 상황

목포대학교 학사 안내, 전남 지역 정책, 공공 복지, 관광, 기술 문서 등 하나의 도메인을
고른다. 사용자가 자연어 질의를 입력하면 관련 문서의 순위를 반환하는 검색기를 만든다.

예를 들어 “청년이 받을 수 있는 창업 자금은?”이라는 질의에서 다음 두 문서는 모두
`창업`이라는 단어를 포함할 수 있지만, 실제 관련성은 다르다.

- 문서 A: 청년 예비창업자를 위한 사업화 자금
- 문서 B: 관광 스타트업의 사무공간 지원

이 과제의 목표는 최신 모델을 사용해 그럴듯한 결과를 보여주는 것이 아니다. **어떤
관련성 정의에서 어떤 검색기가 더 낫다고 말할 수 있는지 검증 가능한 증거를 만드는 것**이다.

## 3. 전체 과업

다음 파이프라인을 구현한다.

```text
원문 수집 → 문서 정제 → 질의·qrels 작성 → 개발/평가 분리
         → TF–IDF 검색 ─┐
                        ├→ 동일 지표 계산 → 질의별 비교 → 오류 분석
         → Dense 검색 ──┘
```

필수 비교군은 다음 두 개다.

1. **Sparse baseline**: `TfidfVectorizer` 기반 코사인 검색
2. **Dense system**: 사전학습 문장 임베딩 기반 코사인 또는 내적 검색

BM25, 문자 n-gram, hybrid, reranker는 확장 실험으로 추가할 수 있지만 필수 두 검색기를
대체할 수 없다.

## 5. Part B · 질의와 관련성 정답 구축 — 20점

### B1. 질의 집합

서로 다른 정보 요구를 나타내는 질의 **20개 이상**을 직접 작성한다.

- `dev`: 8개 이상 — 토큰화, 모델, 정규화 등을 선택할 때 사용
- `test`: 12개 이상 — 설계를 고정한 뒤 최종 평가에 한 번 사용

`queries.csv` 스키마:

```text
query_id,query_text,split,query_type,expected_answer
Q001,청년 창업 자금 지원 조건은?,dev,자연어 질의,연령과 지원 내용
```

질의 유형은 최소 네 종류를 포함한다.

- 정확한 기관명·사업명·코드가 필요한 **lexical 질의**
- 동의어 또는 표현 변환이 필요한 **semantic 질의**
- 날짜·수치·부정·조건을 구분해야 하는 **constraint 질의**
- 관련 문서가 없거나 매우 부족한 **out-of-scope 질의**

### B2. 관련성 라벨

각 질의에 대해 후보 문서를 직접 읽고 `qrels.csv`를 작성한다.

|점수|판정 기준|
|---:|---|
|2|질문의 핵심 정보 요구를 직접 충족함|
|1|주제는 관련되지만 핵심 조건이나 답이 부족함|
|0|키워드가 겹쳐도 사용자의 정보 요구를 충족하지 않음|

- 답이 존재하는 질의에는 가능한 경우 관련성 2인 문서를 하나 이상 둔다.
- `0` 문서를 전부 저장할 필요는 없지만, 오류 분석에 사용한 hard negative는 기록한다.
- 모든 `1`과 `2` 라벨에는 `rationale` 한 문장을 작성한다.
- test 라벨은 검색 결과를 보기 전에 초안을 만들고, 결과를 본 뒤 편리하게 바꾸지 않는다.
- 라벨을 수정했다면 이전 값, 수정 이유, 수정 시각을 별도 표에 남긴다.

### B3. 정답 품질 점검

임의의 질의 5개는 동료 한 명에게 독립 판정을 요청한다. 동료는 코드나 검색 결과를 보지
않고 질의와 후보 문서만 읽는다. 완전한 일치율 또는 Cohen's kappa 중 하나를 보고하고,
불일치 사례 2개 이상에서 최종 라벨을 정한 기준을 설명한다. 동료의 qrels를 복사해 개인
과제의 나머지 질의를 대신 작성해서는 안 된다.

## 6. Part C · 검색기 구현 — 20점

두 검색기는 최소한 아래 인터페이스와 동등한 동작을 제공해야 한다. 함수 이름은 달라도
되지만 입력·출력 계약은 Notebook에 명시한다.

```python
def fit(documents: list[dict]) -> None:
    """문서 표현과 검색 인덱스를 준비한다."""

def search(query: str, k: int = 5) -> list[dict]:
    """score 내림차순으로 doc_id, score, rank를 반환한다."""
```

### C1. TF–IDF 기준선 — 8점

- word 또는 character analyzer를 하나 선택하고 선택 이유를 설명한다.
- `ngram_range`, `min_df`, `sublinear_tf`, norm 등 핵심 파라미터를 기록한다.
- query와 document에 **같은 vectorizer**를 사용한다.
- sparse matrix를 불필요하게 dense array로 변환하지 않는다.
- 동점의 순서를 재현 가능하게 정한다. 권장 규칙은 `score desc, doc_id asc`다.

### C2. 밀집 임베딩 검색기 — 8점

- 모델의 정확한 Hugging Face 식별자와 revision을 기록한다.
- pooling, 출력 차원, 정규화 여부, query/document prefix 사용 여부를 기록한다.
- 코사인, 내적 또는 L2 중 하나를 사용하고 모델 카드 또는 실험 근거로 선택을 설명한다.
- 문서 임베딩은 질의마다 다시 계산하지 않고 캐시한다.
- 배치 크기와 device를 기록하고 CPU에서도 작은 샘플이 실행되게 한다.

권장 시작 모델은 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`지만,
다른 공개 모델을 사용해도 된다. 모델 크기만으로 더 좋은 모델이라고 주장할 수 없다.

### C3. 필수 자기 테스트 — 4점

다음 상황을 `assert` 또는 단위 테스트로 확인한다.

1. 동일 문장을 질의하면 자기 문서의 유사도가 높게 나온다.
2. 빈 문자열 또는 OOV에 가까운 질의를 넣어도 예외 없이 정의된 결과를 반환한다.
3. 반환 문서 수는 `min(k, 문서 수)`이며 `doc_id`가 중복되지 않는다.
4. 모든 점수와 순위가 유한값이고 점수 내림차순이다.
5. 같은 seed와 입력으로 두 번 실행하면 같은 순위를 반환한다.

## 7. Part D · 평가 지표 구현과 검증 — 20점

라이브러리 점수를 출력하는 것만으로는 충분하지 않다. 다음 지표를 직접 구현하고 작은
예제의 손계산과 일치하는지 확인한다.

### D1. 필수 지표

$$
P@k=\frac{\text{상위 }k\text{개 중 관련 문서 수}}{k}
$$

$$
R@k=\frac{\text{상위 }k\text{개 중 관련 문서 수}}{\text{전체 관련 문서 수}}
$$

$$
MRR=\frac{1}{|Q|}\sum_{q\in Q}\frac{1}{\operatorname{rank}_q}
$$

$$
nDCG@k=\frac{\sum_{i=1}^{k}\frac{2^{rel_i}-1}{\log_2(i+1)}}{IDCG@k}
$$

- `P@5`, `Recall@5`, `MRR`, `nDCG@5`를 보고한다.
- P/R/MRR의 binary relevance는 `relevance >= 1`로 정의한다.
- nDCG는 0/1/2 graded relevance를 사용한다.
- 관련 문서가 없는 out-of-scope 질의는 일반 Recall 평균에서 제외하고 별도 거부 과제로
  분석한다. 어떤 규칙을 사용했는지 명시한다.

### D2. 손계산 검증 예제

질의 하나의 상위 5개 relevance가 `[2, 0, 1, 0, 0]`이고 전체 관련 문서가 3개일 때,
다음을 손으로 계산해 Markdown 셀에 적고 함수 출력과 비교한다.

- `P@5`
- `Recall@5`
- reciprocal rank
- `DCG@5`, `IDCG@5`, `nDCG@5`

### D3. 통제된 실험

1. dev에서 TF–IDF 설정과 dense 설정을 선택한다.
2. 선택 근거를 표로 기록하고 설정을 동결한다.
3. test에서 두 검색기를 각각 한 번 평가한다.
4. 평균뿐 아니라 질의별 결과를 `per_query_metrics.csv`로 저장한다.
5. 문서 인덱싱 시간, 질의당 평균/p95 지연시간, 표현 행렬 또는 임베딩의 메모리 크기를
   같은 환경에서 측정한다.

`aggregate_metrics.csv`의 필수 열:

```text
system,split,p_at_5,recall_at_5,mrr,ndcg_at_5,index_seconds,
mean_query_ms,p95_query_ms,index_size_mb
```

test의 지표가 예상보다 낮아도 test를 보고 모델을 다시 선택하지 않는다. 낮은 결과를
정직하게 분석하는 것이 재사용된 test에서 높은 점수를 만드는 것보다 중요하다.

## 8. Part E · 오류 분석과 기술 서술 — 20점

### E1. 사례 분석

두 검색기의 결과를 함께 보고 다음을 선정한다.

- 둘 다 성공: 2건 이상
- sparse만 성공: 2건 이상
- dense만 성공: 2건 이상
- 둘 다 실패: 3건 이상

`error_analysis.csv`의 필수 열:

```text
query_id,query_text,system,returned_doc_id,expected_doc_id,
error_type,evidence,root_cause,proposed_fix,fix_tested
```

`error_type`은 다음 통제어휘 중 하나 이상을 사용한다.

- `tokenization`
- `lexical_gap`
- `entity_or_code`
- `negation`
- `number_or_date`
- `long_document`
- `annotation_ambiguity`
- `domain_shift`
- `no_relevant_document`
- `other`

오류 원인을 “모델이 좋지 않다”로 쓰지 않는다. 어떤 토큰, 문장, 점수, 순위 또는 라벨이
오류와 연결되는지 증거를 제시한다. 개선안 한 가지는 실제로 dev에서 적용하고, 지표와
실패 사례가 어떻게 변했는지 보고한다. test에는 개선안을 다시 적용해 선택하지 않는다.

### E2. 필수 서술 문제

보고서에서 다음 질문에 답한다.

1. L2 정규화된 두 벡터에서 코사인 최대화와 유클리드 거리 최소화의 순위가 같은 이유를
   수식으로 보이라.
2. TF–IDF가 고유명사·코드 질의에서 dense보다 유리할 수 있는 이유를 IDF와 토큰화로
   설명하라.
3. dense가 lexical gap을 줄인 실제 사례 하나와, 의미가 비슷하지만 정답 조건이 달라
   실패한 사례 하나를 비교하라.
4. 평균 MRR이 같아도 두 시스템의 사용자 경험이 다를 수 있는 상황을 제시하라.
5. 다음 학기에 데이터가 갱신되면 무엇을 다시 측정해야 하는가?

한다. 모델 다운로드를 제외한 필수 코드는 Colab CPU에서 권장 15분 안에 끝나야 한다.

### 9.2 기술 보고서

- PDF **4쪽 이내**, 참고문헌·부록은 분량에서 제외
- 1쪽: 문제, 데이터, 관련성 정의
- 1쪽: 두 검색기와 수학적 선택
- 1쪽: 정량 결과와 효율 비교
- 1쪽: 오류 분석, 한계, 개선안
- 표와 그림에는 번호·제목을 붙이고 본문에서 해석한다.
- Notebook 출력 화면을 단순 나열하지 않는다.

### 9.3 필수 파일

```text
README.md
assignment01.ipynb
requirements.txt
data/documents.csv
data/queries.csv
data/qrels.csv
results/aggregate_metrics.csv
results/per_query_metrics.csv
results/error_analysis.csv

```

원문 재배포가 허용되지 않으면 `documents.csv` 대신 공개 다운로드 URL, 해시, 수집 스크립트와
작은 비식별 샘플을 제출한다. 채점자가 합법적으로 같은 데이터를 재구성할 수 있어야 한다.

## 10. 채점 기준 — 100점

|영역|배점|완전한 수행의 기준|
|---|---:|---|
|A. 문제정의·데이터|15|100개 이상, 스키마·출처·라이선스·품질·오류비용이 명확|
|B. 질의·qrels|20|20개 이상, dev/test 분리, 라벨 근거와 일부 독립 검증|
|C. 검색기 구현|20|두 검색기 계약 충족, 캐시·동점·예외·자기 테스트 통과|
|D. 평가|20|4개 지표 직접 구현, 손검산, 통제 실험, 효율 측정|
|E. 오류·서술|20|요구 사례 수, 증거 기반 원인, dev 개선 검증, 수식 답변|
|재현성·AI 기록|5|Run all 성공, 버전·seed·경로·AI 검증 기록 완전|

다음 상한을 적용한다.

- TF–IDF 또는 dense 중 하나가 없으면 최대 70점
- test를 모델 선택에 사용하면 최대 70점
- qrels 없이 상위 결과를 주관적으로 평가하면 최대 60점
- Notebook이 실행되지 않으면 재현성 0점이며 실행 가능한 부분만 평가

## 11. 개별 구술 확인

제출 후 5분 내외로 다음 중 일부를 수행한다.

- `k=5`를 `k=10`으로 바꾸기 전에 P@k와 Recall@k의 변화 방향을 예측한다.
- TF–IDF의 analyzer 또는 dense 정규화를 바꾸고 순위 변화를 설명한다.
- 임의 질의의 MRR 또는 nDCG를 손으로 계산한다.
- 실패 사례 한 건에서 제안한 root cause와 증거를 설명한다.
- 자신의 AI 사용 기록 중 하나를 골라 무엇을 검증했는지 보인다.

핵심 구현을 설명하지 못하면 해당 구현 영역은 평가하지 않는다.

## 12. 시작 순서와 권장 체크포인트

1. **체크포인트 1**: 문서 20개로 스키마와 검색 단위를 검증한다.
2. **체크포인트 2**: 질의 5개와 qrels로 TF–IDF end-to-end를 완성한다.
3. **체크포인트 3**: 문서 100개·질의 20개로 확장하고 split을 동결한다.
4. **체크포인트 4**: dense 검색기를 같은 평가 함수에 연결한다.
5. **체크포인트 5**: test를 열기 전에 설정·가설·예상 실패를 기록한다.
6. **체크포인트 6**: test 1회 평가 후 보고서와 결과 CSV의 수치를 대조한다.

## 13. 자주 묻는 질문

**Q. 제공된 `policy_documents.csv` 8개만 사용해도 되는가?**
아니다. 해당 파일은 파이프라인 디버깅용이다. 최종 평가는 100개 이상의 독립 문서가 필요하다.

**Q. OpenAI 등 유료 embedding API를 사용해도 되는가?**
가능하지만 필수 기준선은 API 없이 실행되어야 하고, API 모델·버전·비용·실행일을 기록해야
한다. 키를 제출하면 안 된다.

**Q. dense가 기준선보다 낮으면 감점되는가?**
낮다는 이유 자체로 감점하지 않는다. 평가가 공정하고 실패 원인을 증거로 설명했는지가
중요하다.

**Q. test 성능이 낮아 설정을 한 번만 더 바꾸면 안 되는가?**
그 변경은 다음 실험의 가설로 기록할 수 있지만 같은 test의 최종 점수를 다시 선택하면 안 된다.

**Q. 보고서의 코드를 모두 설명해야 하는가?**
핵심 코드는 Notebook에 두고, 보고서에는 설계·수식·결과·한계를 설명한다.
