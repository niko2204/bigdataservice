# 최종 프로젝트 · 작은 임베딩 데이터 서비스

> 실제 사용자가 입력을 넣으면 검색·분류·추천 결과를 보여주는 작은 서비스를 만들고,
> 단순한 기준선보다 무엇이 좋아졌는지 설명한다.

|항목|내용|
|---|---|
|수행 형태|개인 또는 2–3인 팀|
|교과목 반영|25%|
|권장 시간|개인 15–20시간, 팀은 역할 분담|
|진행|6주차 제안 → 8주차 중간 확인 → 10주차 제출·발표|
|최소 비교|기준선 1개 + 임베딩 방법 1개|
|제출|Notebook/코드, 평가 CSV, PDF 4쪽, 10분 발표·시연|

공통 실행·제출 규칙은 [과제 안내](README.md)를 먼저 읽는다.

---

## 1. 프로젝트의 핵심

최종 프로젝트는 거대한 AI 서비스를 만드는 과제가 아니다. 다음 문장을 실제 데이터와
수치로 완성하는 것이 목표다.

> “우리는 **어떤 사용자**가 **어떤 입력**을 넣었을 때 **어떤 결과**를 받는 시스템을
> 만들었다. 단순 기준선과 비교했을 때 **어떤 지표**가 달라졌지만, **어떤 상황**에서는
> 여전히 실패했다.”

예:

> “재학생이 자연어로 장학 정보를 검색하는 시스템을 만들었다. TF–IDF보다 밀집 임베딩 검색의
> 재현율@5가 높았지만, 정확한 사업 코드가 포함된 질의에서는 TF–IDF가 더 좋았다.”

## 2. 먼저 정할 여섯 가지

제안서와 최종 보고서에 다음을 적는다.

|항목|쉬운 질문|
|---|---|
|사용자|누가 이 시스템을 사용하는가?|
|입력|사용자가 문장, 문서, 이미지 중 무엇을 넣는가?|
|출력|검색 순위, 분류 라벨, 추천 목록, 답변 중 무엇을 받는가?|
|기준선|가장 단순하게 해결한다면 어떤 방법을 쓰는가?|
|성공 지표|어떤 숫자가 좋아지면 성공이라고 할 수 있는가?|
|위험한 오류|어떤 잘못된 결과가 사용자에게 가장 큰 문제인가?|

이 여섯 가지를 한 문장으로 설명할 수 없다면 데이터 수집이나 UI 개발을 시작하지 않는다.

## 3. 다섯 트랙 중 하나 선택

### Track A · 문서 검색

**예시:** 학사 안내, 정책, 관광, 기술문서 검색

- 문서 100개 이상
- 개발 질의 5개 + 최종 평가 질의 10개 이상
- 기준선: TF–IDF 또는 BM25
- 임베딩 방법: 밀집 문장 임베딩 검색
- 필수 지표: 재현율@5, MRR

### Track B · 근거 기반 RAG

**예시:** 학교 규정 또는 공공 지원사업 질의응답

- 원문 20개 이상, 청크 100개 이상
- 개발 질문 5개 + 최종 평가 질문 10개 이상
- 전체 질문 중 답변 불가 질문 4개 이상
- 기준선: TF–IDF 검색 + 추출형 답변
- 임베딩 방법: 밀집/혼합 검색 + 근거 답변
- 필수 지표: 재현율@3, 정답 비율, 올바른 응답 보류 비율

### Track C · 문서 분류

**예시:** 민원·정책·뉴스의 범주 분류

- 라벨이 있는 문서 200개 이상
- 클래스 3개 이상
- 학습/개발/최종 평가 분리
- 기준선: TF–IDF + Logistic Regression
- 임베딩 방법: 문장 임베딩 + Logistic Regression
- 필수 지표: 정확도, 매크로 F1, 혼동행렬

### Track D · 추천

**예시:** 강좌, 논문, 관광 콘텐츠 추천

- 추천 대상 100개 이상
- 사용자 행동을 쓴다면 사용자 30명·상호작용 300건 이상
- 사용자 행동이 없다면 평가용 선호/관련성 쌍 50개 이상 직접 작성
- 기준선: 인기순, 범주 일치 또는 TF–IDF 유사도
- 임베딩 방법: 항목 임베딩 유사도 추천
- 필수 지표: 재현율@10, 응답률(coverage)

### Track E · 텍스트–이미지 검색

**예시:** 관광지, 안전장비, 시설 이미지 검색

- 이미지–텍스트 쌍 100개 이상
- 개발 질의 5개 + 최종 평가 질의 10개 이상
- 기준선: 이미지 설명의 TF–IDF 검색 또는 범주 일치
- 임베딩 방법: CLIP 계열 멀티모달 임베딩
- 필수 지표: 재현율@1, 재현율@5, MRR

최소 규모를 바꿔야 한다면 6주차 제안서 단계에서 교수자와 먼저 협의한다.

## 4. 프로젝트 진행 순서

```text
1쪽 제안서
   ↓
작은 데이터 10개로 전체 흐름 확인
   ↓
기준선 완성
   ↓
임베딩 방법 연결
   ↓
개발에서 개선 한 가지 시도
   ↓
최종 평가 데이터로 최종 성능 측정
   ↓
오류 5건 분석
   ↓
간단한 입력 화면·발표
```

### 가장 중요한 원칙

먼저 기준선을 완성한다. 임베딩 모델이나 Streamlit 화면부터 만들면 데이터와 평가가 뒤로
밀려 프로젝트가 끝나지 않을 가능성이 높다.

## 5. 단계 1 · 제안서 — 6주차

PDF 1쪽을 제출하고 2분 동안 설명한다.

1. 제목과 팀원
2. 사용자, 입력, 출력
3. 데이터 출처와 예상 개수
4. 기준선과 임베딩 방법
5. 개발/최종 평가와 평가 지표
6. 가장 걱정되는 오류 한 가지
7. 팀원별 역할

### 제안서 예시

```text
제목: 목포대학교 장학 안내 검색
사용자: 장학 제도를 찾는 재학생
입력/출력: 자연어 질문 → 관련 문서 5개
데이터: 공개 학사 안내 120건
기준선/임베딩: TF–IDF / 다국어 MiniLM
평가: 개발 5개, 최종 평가 10개, 재현율@5와 MRR
위험: 신청 기한이 다른 문서를 잘못 추천할 수 있음
```

데이터를 구할 수 없거나 정답을 만들 수 없는 주제는 범위를 바꾸어야 한다.

## 6. 단계 2 · 데이터와 정답 준비 — 15점

### 6.1 데이터 카드

[데이터 카드 템플릿](templates/DATA_CARD.md)을 사용하되, 다음 여섯 항목만 필수로 작성한다.

1. 데이터 이름과 출처
2. 데이터 한 행이 의미하는 것
3. 데이터 개수와 주요 범주
4. 수집·전처리 방법
5. 라이선스 또는 이용 근거
6. 부족하거나 편향된 부분

### 6.2 정답 데이터

트랙에 맞는 정답을 준비한다.

- 검색/RAG/멀티모달: 질의별 정답 문서·이미지
- 분류: 각 문서의 클래스 라벨
- 추천: 사용자별 관련 항목 또는 선호 쌍

설정을 조정하는 개발 데이터와 마지막 평가용 최종 평가 데이터를 구분한다. 같은 문서나 거의 같은 문장이
여러 분할에 들어가지 않도록 확인한다.

### 6.3 데이터 확인 코드

```python
assert len(data) >= minimum_size
assert data["id"].is_unique
assert data["text"].fillna("").str.strip().ne("").all()
```

트랙에 맞게 열 이름을 바꾸어 사용한다.

## 7. 단계 3 · 기준선 구현 — 15점

기준선은 새 방법의 가치를 확인하는 출발점이다.

|트랙|권장 기준선|
|---|---|
|검색/RAG|TF–IDF 또는 BM25|
|분류|TF–IDF + Logistic Regression|
|추천|인기순, 범주 일치 또는 TF–IDF 유사도|
|텍스트–이미지 검색|이미지 설명 TF–IDF 또는 범주 일치|

기준선 단계에서 다음이 모두 동작해야 한다.

- 데이터 로딩
- 개발 예측 또는 검색
- 지표 계산
- 질의/예제별 결과 저장

기준선이 실행되지 않으면 임베딩 방법으로 넘어가지 않는다.

---

## 8. 단계 4 · 임베딩 방법 구현 — 20점

트랙에 맞는 공개 임베딩 모델 하나를 선택한다. 모델을 여러 개 비교할 필요는 없다.

기록할 내용:

- 모델 저장소 이름
- 입력으로 사용한 열
- 임베딩 차원
- 정규화 여부
- cosine, inner product 또는 분류기 중 사용 방법

### 공통 확인

1. 임베딩 개수가 데이터 개수와 같은가?
2. 임베딩에 `NaN`이나 무한대가 없는가?
3. 검색 결과나 예측 결과가 ID와 연결되는가?
4. 같은 입력을 다시 실행하면 결과가 같은가?

복잡한 미세 조정은 필수가 아니다. 사전학습 모델의 frozen 임베딩만 사용해도 된다.

---

## 9. 단계 5 · 개선 실험 한 가지 — 15점

개발에서 기준선과 임베딩 방법을 비교한 뒤 개선 한 가지만 시도한다.

예:

- 검색: TF–IDF와 밀집 임베딩 순위를 간단히 결합
- RAG: 청크 크기 한 번 변경
- 분류: 클래스 가중치 적용
- 추천: 범주 필터 추가
- 멀티모달: 한국어/영어 프롬프트 비교

다음 표를 작성한다.

|실험|무엇을 바꿨는가?|예상|개발 결과|선택|
|---|---|---|---|---|
|E1|밀집에 TF–IDF 순위 결합|코드 질의 개선|재현율 +0.08|사용|

최종 평가 결과를 본 뒤 개선안을 선택하지 않는다. 개선이 실패해도 이유를 설명하면 된다.

## 10. 단계 6 · 최종 평가와 오류 5건 — 20점

### 10.1 최종 성능 평가

설정을 고정한 뒤 기준선과 최종 시스템을 같은 최종 평가에서 비교한다.

```csv
system,split,metric_1,metric_2
baseline,test,0.61,0.55
embedding,test,0.74,0.68
```

트랙에서 지정한 지표를 사용한다. 평균 결과와 함께 각 질의·문서·사용자별 결과도 CSV로
저장한다.

### 10.2 오류 사례 5건

최소 5개의 서로 다른 실패를 분석한다.

```csv
input,expected,observed,error_type,reason,possible_fix
장학금 B-17 서식,D017,D003,정확한 코드,임베딩이 코드를 구분하지 못함,TF–IDF 결합
```

가능한 오류 유형:

- 동의어 또는 같은 단어 부족
- 고유명사·코드·숫자·날짜·부정
- 너무 긴 입력 또는 청크 문제
- 잘못된 데이터·라벨
- 특정 범주만 성능이 낮음
- 근거가 없는데 답함

개선 방법은 제안만 해도 되며 모두 다시 구현할 필요는 없다.

---

## 11. 단계 7 · 간단한 서비스 시연 — 5점

다음 중 하나를 사용한다.

- Notebook의 입력 함수
- 간단한 CLI
- Streamlit 또는 Gradio 화면

필수 동작:

1. 사용자가 새 입력을 넣는다.
2. 검색·분류·추천·답변 결과가 나타난다.
3. 점수, 근거 또는 주의사항 하나 이상을 보여준다.
4. 준비된 예제뿐 아니라 발표 중 받은 새 입력도 실행할 수 있다.

UI 디자인은 평가의 중심이 아니다. Notebook 함수만으로도 모든 점수를 받을 수 있다.

## 14. 발표

## 15. 팀 프로젝트 규칙

- 모든 팀원은 전체 프로젝트의 목적, 데이터, 기준선과 지표를 설명할 수 있어야 한다.
- `CONTRIBUTIONS.md`에 각자 맡은 일을 간단히 기록한다.

```markdown
|팀원|주요 역할|만든 파일/실험|검토한 다른 부분|
|---|---|---|---|
```

- 코드만이 아니라 데이터 정리, 정답 작성, 실험, 오류 분석과 보고서도 기여다.
- 자신의 핵심 작업을 설명하지 못하면 개인 점수를 조정할 수 있다.

## 16. 채점 기준 — 100점

|영역|배점|확인 내용|
|---|---:|---|
|문제정의|10|사용자·입력·출력·지표·위험한 오류가 분명함|
|데이터와 정답|15|트랙 최소 규모, 출처·라이선스, 개발/최종 평가, 데이터 카드|
|기준선|15|간단한 방법이 전체 시스템으로 실행되고 평가됨|
|임베딩 시스템|20|모델·표현·점수 설명, 실행·ID 연결·기본 테스트|
|개선 실험|15|개발에서 한 가지 변경을 공정하게 비교|
|최종 평가·오류|20|최종 평가 비교, 트랙 지표, 질의별 결과, 오류 5건|
|시연·재현성|5|새 입력, Run all, 카드·AI·팀 기록|

기준선이 없으면 최대 75점이다. 최종 평가를 보고 모델이나 개선안을 선택하면 평가 영역의 완전한
점수를 받을 수 없다. 예시 화면만 있고 수치 평가가 없으면 최대 70점이다.

## 17. 제출 전 체크리스트

- [ ] 사용자를 한 문장으로 설명할 수 있다.
- [ ] 선택 트랙의 최소 데이터와 질의/라벨 수를 충족한다.
- [ ] 기준선과 임베딩 방법이 모두 실행된다.
- [ ] 개발에서 개선 한 가지를 시도했다.
- [ ] 최종 평가에서 두 방법을 같은 지표로 비교했다.
- [ ] 서로 다른 실패 사례 5건을 설명했다.
- [ ] 새 입력으로 결과를 시연할 수 있다.
- [ ] Notebook이 새 런타임에서 실행된다.
- [ ] 데이터 카드, 모델 카드와 AI 사용 기록이 있다.
