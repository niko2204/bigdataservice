# 최종 프로젝트 · 임베딩 기반 데이터 서비스 설계와 방어

> **최종 목표:** 실제 사용자의 의사결정을 돕는 임베딩 기반 시스템을 만들고, 기준선 대비
> 개선·실패·비용·위험을 재현 가능한 실험과 개별 구술로 방어한다.

|항목|내용|
|---|---|
|수행 형태|개인 또는 2–3인 팀, 개인 프로젝트는 동일 요구 수준 적용|
|교과목 반영|25%|
|권장 작업량|1인 25–35시간, 팀은 역할별 동등 기여|
|진행 기간|6주차 제안 → 8주차 중간점검 → 10주차 최종 제출·시연|
|선택 트랙|검색, RAG, 분류, 추천, 텍스트–이미지 검색|
|제출|제안서, 중간보고, 코드·Notebook, 평가 데이터, 보고서, 카드, 발표·시연|

마감 시각과 제출 위치는 LMS 공지를 따른다. 공통 실행·협업·AI 정책은
[과제 운영 안내](README.md)를 먼저 읽는다.

---

## 1. 프로젝트가 답해야 하는 질문

좋은 프로젝트는 “모델을 사용했다”가 아니라 다음 주장에 답한다.

1. **누구의 어떤 의사결정**을 돕는가?
2. 원 데이터의 어떤 관계를 임베딩 공간에 보존하려는가?
3. 단순 기준선보다 실제로 나은가? 어떤 질의·집단에서는 나쁘지 않은가?
4. 성능 향상이 모델, 데이터, 전처리, 검색 또는 평가 변경 중 무엇에서 왔는가?
5. 실패했을 때 사용자는 어떤 피해를 입으며 시스템은 어떻게 멈추거나 알리는가?
6. 타인이 같은 데이터·코드·환경에서 주장을 재검증할 수 있는가?

## 2. 학습목표

프로젝트를 완료하면 다음을 할 수 있어야 한다.

- 모호한 서비스 아이디어를 입력·출력·사용자·오류비용·성공 지표가 있는 문제로 바꾼다.
- 데이터 출처, 분할, 라벨, 누수, 라이선스와 대표성 한계를 데이터 카드로 설명한다.
- 임베딩 시스템과 최소 기준선을 동일 조건에서 비교한다.
- dev에서 설계를 선택하고 test에서 최종 성능을 한 번 보고한다.
- 정확도, 효율, 비용, 공정성, 근거성을 함께 평가한다.
- 평균 점수 뒤에 숨은 실패 유형과 하위집단 성능을 분석한다.
- 재현 가능한 코드와 모델·시스템 카드를 작성한다.
- 팀 프로젝트에서도 자신의 기여와 전체 시스템을 개별적으로 설명한다.

## 3. 선택 트랙과 최소 규모

아래 다섯 트랙 중 하나를 선택한다. 여러 트랙을 결합할 수 있지만, 범위를 넓힌다는 이유로
각 트랙의 핵심 평가를 생략할 수 없다.

### Track A · 의미 검색

**예시:** 학사 규정 검색, 지역 정책 검색, 기술문서 검색

- 문서 200개 이상
- dev 10개 + test 20개 이상의 질의
- graded qrels `0/1/2`
- 기준선: TF–IDF 또는 BM25
- 임베딩 시스템: dense 또는 multi-vector
- 필수 지표: Recall@5, MRR, nDCG@5, p95 latency
- 확장 후보: hybrid, reranker, metadata filter

### Track B · 근거 기반 RAG

**예시:** 학교 규정 질의응답, 공공 지원사업 안내

- 원문 50개 이상, 최종 chunk 200개 이상
- dev 12개 + test 20개 이상의 질문
- test에 unanswerable 질문 5개 이상
- 기준선: sparse retrieval + extractive/규칙 answerer
- 임베딩 시스템: dense/hybrid retrieval + grounded answerer
- 필수 지표: Recall@5, answer correctness, citation precision/recall,
  abstention accuracy, unsupported claim rate
- retrieval, generation, citation, abstention 오류를 분리

### Track C · 문서 분류

**예시:** 민원 유형, 정책 분야, 논문 주제 분류

- 라벨 데이터 500개 이상, 클래스 3개 이상
- train/dev/test를 라벨 또는 시간 기준으로 분리
- 기준선: TF–IDF + Logistic Regression 또는 Linear SVM
- 임베딩 시스템: frozen embedding + classifier 또는 fine-tuned encoder
- 필수 지표: macro F1, 클래스별 precision/recall, confusion matrix, 추론시간
- 클래스 불균형, 중복 문서, 라벨 누수와 하위집단 오류 분석

### Track D · 추천

**예시:** 강좌·논문·관광 콘텐츠·정책 추천

- 추천 대상 item 300개 이상
- 상호작용 기반이면 사용자 50명 이상·상호작용 1,000건 이상
- 상호작용이 없으면 content-based 과제로 명시하고 평가용 선호/관련성 쌍 100개 이상 구축
- 기준선: 인기순, 범주 일치 또는 TF–IDF 유사도 중 하나
- 임베딩 시스템: item/user representation 기반 추천
- 필수 지표: Recall@10, nDCG@10, coverage, diversity 또는 novelty 중 하나
- 무작위 split이 미래 정보를 누수하지 않는지 확인하고 가능하면 시간 분할 사용

### Track E · 텍스트–이미지 검색

**예시:** 관광 이미지, 시설 사진, 안전장비 이미지 검색

- 이미지–텍스트 pair 200개 이상
- dev 10개 + test 20개 이상의 텍스트 질의
- 기준선: 이미지 메타데이터의 TF–IDF 검색 또는 범주 일치
- 임베딩 시스템: CLIP 계열 또는 동등한 멀티모달 모델
- 필수 지표: Recall@1/5/10, MRR, 언어·질의 유형별 성능, p95 latency
- 한국어/영어 prompt, 구체적/추상적 질의, 시각적으로 유사한 hard negative 비교

### 규모 변경

개인정보·저작권·GPU 제약 때문에 최소 규모를 충족하기 어렵다면 **제안서 단계에서** 교수자
승인을 받는다. 최종 제출 직전에 데이터 규모를 줄이고 사후 설명하는 것은 승인으로 보지 않는다.

## 4. 공통 시스템 요구사항

### 4.1 문제 계약

제안서와 최종 보고서 첫 표에 다음을 고정한다.

|항목|답해야 할 내용|
|---|---|
|사용자|누가 어떤 맥락에서 쓰는가?|
|의사결정|출력으로 무엇을 선택·판단하는가?|
|입력|문장, 문서, 이미지, 사용자 이력 중 무엇인가?|
|출력|순위, 라벨, 추천, 답변과 근거 중 무엇인가?|
|보존 관계|무엇이 가까워야 하고 무엇이 멀어야 하는가?|
|고비용 오류|가장 위험한 false positive/negative는 무엇인가?|
|성공 기준|어떤 test 지표가 얼마 이상이어야 하는가?|
|사용 금지|어떤 결정에 단독으로 사용하면 안 되는가?|

### 4.2 기준선

최소 두 수준을 비교한다.

1. **단순 또는 비학습 기준선**: random, popularity, majority, category match 중 과업에 맞는 것
2. **강한 고전 기준선**: TF–IDF/BM25, Logistic Regression, metadata rule 등
3. **제안 임베딩 시스템**

1과 2가 같은 경우에는 교수자 승인 아래 두 시스템만 비교할 수 있다. 최신 모델끼리만 비교해
“임베딩이 유용하다”고 주장할 수 없다.

### 4.3 임베딩 명세

다음을 코드와 모델 카드에 기록한다.

- 모델 저장소 ID, revision 또는 체크섬
- 입력 전처리와 최대 길이
- 토큰/문장/문서/이미지 중 출력 단위
- 출력 차원과 dtype
- pooling과 정규화
- cosine, inner product, L2 또는 learned score
- query/document prefix 또는 prompt template
- batch size, device, 인덱스 타입

### 4.4 데이터 분할

- train/dev/test 또는 dev/test 역할을 명시한다.
- 같은 원문·사용자·시간 구간·중복 샘플이 split을 넘지 않게 한다.
- 모델, threshold, prompt, chunk, feature 선택은 dev에서 끝낸다.
- test는 최종 설정 평가에 한 번 사용한다.
- 외부 공개 benchmark를 test로 쓰면 학습·튜닝에 포함되었을 가능성을 한계로 기록한다.

## 5. 단계별 마일스톤

### Milestone 1 · 제안서 — 6주차

PDF 2쪽과 3분 구두 설명을 제출한다.

1. 프로젝트 제목과 팀원
2. 사용자·문제·입력·출력·오류비용
3. 데이터 출처, 이용 근거, 예상 규모, 작은 샘플 10개
4. 기준선과 제안 임베딩 시스템
5. dev/test 구성과 평가 지표
6. 가장 큰 기술·데이터·윤리 위험 세 가지
7. 주차별 작업 계획과 팀원별 책임

**승인 조건:** 데이터 접근 가능성, 정답 작성 가능성, 기준선, test 평가, 4주 내 실행 가능성이
모두 확인되어야 한다. “Streamlit 앱을 만든다”처럼 모델·데이터·평가가 없는 제안은 승인하지
않는다.

### Milestone 2 · 중간점검 — 8주차

다음이 실행되는 Notebook과 5분 시연을 제출한다.

- 전체 데이터의 50% 이상 수집·정제
- 기준선 end-to-end 실행
- dev 정답 집합 50% 이상 작성
- 제안 시스템의 최소 동작 경로
- 첫 정량 결과표
- 실패 사례 5건 이상
- 남은 위험과 일정 수정

중간점검에서 test를 먼저 보고 최고 결과를 선택하면 최종 평가의 test로 사용할 수 없다.

### Milestone 3 · 최종 제출 — 10주차

모든 코드·데이터 참조·정량 평가·보고서·카드·발표자료를 제출하고 서비스를 시연한다.

## 6. 실험 설계 요구사항

### 6.1 가설표

실험 전에 최소 세 개의 가설을 작성한다.

|ID|변경 요소|예상되는 지표 변화|예상 실패/부작용|검증 split|
|---|---|---|---|---|
|H1|TF–IDF → dense|semantic 질의 Recall 증가|코드 질의 하락|dev|

결과를 본 뒤 가설 문장을 유리하게 바꾸지 않는다. 틀린 가설도 왜 틀렸는지 설명하면 중요한
결과다.

### 6.2 통제 비교

- 데이터와 평가 정답을 고정하고 한 번에 한 요소를 바꾼다.
- 최소 3개 시스템/조건을 같은 지표로 비교한다.
- 모델 파라미터 수가 아니라 과업 지표·효율·오류로 선택한다.
- 평균과 질의/클래스/사용자별 결과를 모두 저장한다.
- 가능한 경우 bootstrap 95% confidence interval을 보고한다.
- 표본이 작아 유의성을 주장할 수 없으면 그 사실을 명시한다.

### 6.3 Ablation 또는 반증 실험

최소 두 가지를 수행한다.

- L2 normalization 제거
- query prefix 제거
- overlap 제거
- hybrid의 sparse 또는 dense 구성요소 제거
- metadata filter 제거
- reranker 제거
- 한국어 prompt를 영어 prompt로 교체
- hard negative 제외

Ablation은 서로 다른 모델 여러 개를 나열하는 것이 아니라, 제안 시스템의 어떤 구성요소가
성능에 기여했는지 확인하는 실험이다.

### 6.4 효율·비용

정확도 외에 다음을 같은 환경에서 측정한다.

- 전처리·학습·인덱싱 시간
- 평균/p95 추론 또는 검색 지연시간
- 모델·인덱스·캐시 크기
- GPU/CPU와 최대 메모리
- API를 쓰면 요청당 토큰·비용·실패율

서비스 목표에 따라 허용 가능한 latency와 비용 예산을 먼저 정하고 측정값과 비교한다.

## 7. 오류·편향·안전 분석

최소 **10개의 고유 실패 사례**를 유형화한다. 같은 원인의 유사 사례를 10번 복사해 채우지
않는다.

### 공통 오류 유형

- tokenization 또는 긴 입력 truncation
- lexical gap 또는 의미 과일반화
- 고유명사·코드·숫자·날짜·부정
- 데이터/라벨 오류
- domain 또는 temporal shift
- 특정 범주·지역·집단 성능 하락
- 임계값·top-k·cluster 수 선택
- 검색/생성/인용/거부 단계 오류
- latency·memory·API failure

각 사례는 다음을 포함한다.

```text
input → expected output → observed output → diagnostic evidence
→ root cause hypothesis → proposed fix → fix tested on dev?
```

### 하위집단 분석

과업에 맞는 두 개 이상의 slice를 정의한다. 예:

- 짧은/긴 질의
- 고유명사 포함/미포함
- 한국어/영어 혼합
- 다수/소수 클래스
- 지역·기관·시기별 데이터

slice별 지표와 표본 수를 함께 보고한다. 표본이 적으면 일반화하지 않는다.

### 데이터·모델 카드

- [데이터 카드](templates/DATA_CARD.md)
- [모델·시스템 카드](templates/MODEL_CARD.md)

두 카드는 최종 산출물에 반드시 포함한다.

## 8. 구현과 테스트 요구사항

### 8.1 코드 구조

Notebook 하나에 모든 코드를 숨기지 않는다. 최소한 다음 책임을 함수 또는 모듈로 분리한다.

```text
data loading / validation
representation or embedding
model or index construction
prediction or retrieval
metric computation
error analysis and export
service interface
```

### 8.2 필수 테스트

`tests/` 또는 Notebook의 독립 테스트 셀에서 다음을 검증한다.

1. 데이터 ID 고유성, 필수 열, 빈 입력
2. 임베딩 shape, finite value, 정규화 조건
3. metric 함수의 손계산 예제
4. 동일 seed의 결정성
5. train/dev/test 중복·누수
6. 입력이 없거나 범위 밖일 때의 안전한 동작
7. 저장한 모델/인덱스를 다시 불러와 같은 결과를 반환하는 smoke test

교수자는 공개 예제와 다른 입력, 빈 값, 동점, 긴 문자열과 out-of-domain 사례로 핵심 함수를
확인할 수 있다. 하드코딩한 예제 순위만 반환하는 구현은 점수를 받을 수 없다.

### 8.3 최소 서비스 시연

Streamlit, Gradio, CLI 또는 Notebook widget 중 하나를 선택한다. UI의 화려함보다 다음이
중요하다.

- 사용자가 입력을 제공한다.
- top-k, 라벨, 추천 또는 답변이 반환된다.
- 점수·근거·한계 중 하나 이상을 보여준다.
- 범위 밖 입력과 오류를 처리한다.
- 시연용 예제뿐 아니라 현장에서 받은 새 입력도 실행한다.

### 9.2 기여 기록

|주차|팀원|계획|실제 작업|commit/Colab 증거|다음 작업|

기여가 현저히 불균형하거나 핵심 시스템을 설명하지 못하면 팀 점수와 별도로 개인 점수를

## 11. 채점 기준 — 100점

|영역|배점|완전한 수행의 기준|
|---|---:|---|
|문제정의·관련 연구|10|사용자·의사결정·오류비용·성공 기준과 선행 방법의 차이가 구체적|
|데이터·평가 정답|15|출처·라이선스·규모·분할·라벨·누수·카드가 명확|
|기준선·시스템 구현|20|강한 기준선과 임베딩 시스템, 명세·모듈·테스트·예외처리 완전|
|실험·정량 평가|20|dev/test 분리, 적절한 지표, 효율, 3개 조건, 2개 ablation, 재계산 가능|
|오류·편향·안전|15|10개 이상 고유 실패, slice 분석, 근거 기반 원인, 제한·안전 동작|
|재현성·카드|10|새 환경 Run all, 버전·seed·환경·데이터 재구성·비밀정보 관리|
|발표·서비스 시연|5|시간 내 핵심 주장과 새 입력 시연, 결과와 한계 설명|
|개인 기여·구술|5|기여 증거, 핵심 코드 변경·수식·결과를 독립적으로 설명|

### 총점 상한

- 기준선이 없으면 최대 70점
- test를 모델·prompt·임계값 선택에 사용하면 최대 70점
- 수치 평가 없이 예시 화면만 제시하면 최대 60점
- 데이터 출처·이용 근거가 없으면 데이터 영역 0점
- 코드와 데이터가 재현되지 않으면 재현성 0점, 실행 가능한 부분만 평가
- 팀원이 자신의 핵심 기여를 설명하지 못하면 해당 구현 영역을 개인 점수에 반영하지 않음

## 12. 개별 구술 방어

팀 여부와 관계없이 학생별 7분 내외로 진행한다.

1. 임의의 metric 또는 similarity를 작은 예제로 계산한다.
2. 코드의 한 파라미터를 변경하기 전에 결과 방향을 예측한다.
3. test 사례 하나를 골라 입력 → 표현 → 점수 → 출력 경로를 추적한다.
4. 기준선보다 좋아진 이유를 ablation과 오류 사례로 설명한다.
5. 가장 위험한 실패와 운영 시 안전장치를 설명한다.
6. 생성형 AI가 제안한 코드 중 검증·수정한 사례를 보인다.

구술은 발표 암기가 아니라 제출물의 소유권과 이해를 확인하는 과정이다.

## 13. 생성형 AI와 공개 코드

- 브레인스토밍, 코드 설명, 디버깅, 테스트 생성, 문장 교정에 사용할 수 있다.
- AI가 생성한 데이터 라벨은 사람이 검수하고 검수 비율과 오류를 보고한다.
- AI가 만든 synthetic test만으로 최종 성능을 주장할 수 없다.
- 외부 코드·모델·데이터는 파일 또는 보고서 가까이에 URL·라이선스·변경점을 기록한다.
- [AI 사용 기록 템플릿](templates/AI_USAGE.md)에 핵심 대화와 검증을 남긴다.
- 개별 구술에서 설명할 수 없는 AI 생성 코드는 평가하지 않는다.

## 15. 자주 묻는 질문

**Q. 성능이 가장 높은 모델을 사용해야 하는가?**
아니다. 정확도–지연시간–비용–메모리–위험을 함께 비교해 서비스에 적합한 모델을 선택한다.

**Q. 데이터 규모가 최소 조건보다 작지만 라벨 품질이 높다.**
제안서 단계에서 정답 구축 비용과 통계적 한계를 근거로 범위 변경 승인을 받아야 한다.

**Q. test를 여러 번 실행하는 것도 금지인가?**
재현 확인을 위한 동일 설정 재실행은 가능하다. test 결과를 보고 모델·prompt·threshold를
바꿔 최고 점수를 선택하는 것이 금지된다.

**Q. 서비스 UI를 잘 만들면 모델 성능이 낮아도 보완되는가?**
UI는 시연 일부다. 평가 가능한 모델·검색 성능과 오류 분석을 대체하지 못한다.

**Q. 논문과 같은 성능이 나오지 않으면 실패인가?**
아니다. 데이터·모델·하드웨어 차이를 설명하고 재현 가능한 실험으로 원인을 좁히는 것이
학습목표다.

**Q. 팀원 모두가 모든 코드를 작성해야 하는가?**
그럴 필요는 없지만 모든 팀원은 전체 파이프라인과 주요 설계 선택을 설명하고, 자신의 기여를
실행·변경·방어할 수 있어야 한다.
